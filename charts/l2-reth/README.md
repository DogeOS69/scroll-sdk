# l2-reth

Helm chart for Scroll/DogeOS reth based L2 rollup nodes.

This chart supports three roles through `role`:

- `rpc`: RPC node. `controller.replicas` may be greater than 1. Data storage is always rendered as StatefulSet `volumeClaimTemplates`, so every replica gets its own PVC.
- `sequencer`: Sequencer node. `controller.replicas` must be `0` or `1`.
- `bootnode`: Bootnode node. `controller.replicas` must be `0` or `1`.

The chart generates `rollup-node node` as Kubernetes `command`/`args` instead of using shell string concatenation. This avoids argument quoting issues for flags such as `--signer.aws-kms-key-id`.

Use `reth.extraArgs` for rollup-node flags that are not modeled by the chart yet. It can be configured as a whitespace-delimited string:

```yaml
reth:
  extraArgs: "--foo bar --xx --foo2 bar2"
```

It can also be configured as a list, which is safer when an argument value contains spaces:

```yaml
reth:
  extraArgs:
    - --foo
    - bar
    - --xx
    - --foo2
    - bar2
```

The `wait-for-l1.sh` script is mounted from the shared `wait-for-l1-script` ConfigMap generated by the `scroll-common` chart.

`service.main.fullname` optionally overrides only the Kubernetes Service name. This
is useful when the Helm release must keep a reth-specific name for StatefulSet
and PVC stability, while clients keep using an existing DNS name:

```yaml
service:
  main:
    fullname: l2-rpc
```

For example, install or upgrade the release as `l2-reth-rpc` so StatefulSet and
PVC names stay release-derived, then set `service.main.fullname: l2-rpc` when the
client-facing Service DNS should move to reth. Do not use
`global.fullnameOverride` for this migration because it also changes names used
by workloads and storage.

`reth.nodeKey.mode` controls where the p2p node key comes from:

- `secret`: mount a Kubernetes Secret.
- `pvcAutoGenerate`: generate one node key per PVC, useful for RPC replicas.
- `none`: do not pass `--p2p-secret-key`.

For `secret`, `reth.nodeKey.secretName` defaults to `<fullname>-secret-env`, matching the External Secrets convention used by the other production charts in this repo. Override `reth.nodeKey.secretName` only when the Secret has a non-standard name. `reth.nodeKey.secretKey` is the key inside that Secret and defaults to `RETH_NODEKEY`.

When `reth.signer.type` is `localFile`, `reth.signer.localFile.secretName` also defaults to `<fullname>-secret-env`, and `reth.signer.localFile.secretKey` defaults to `RETH_SEQUENCER_SIGNER_PRIVATE_KEY`. This allows a sequencer deployment to source both `RETH_NODEKEY` and `RETH_SEQUENCER_SIGNER_PRIVATE_KEY` from the same `*-secret-env` ExternalSecret target.

Example:

```yaml
reth:
  nodeKey:
    mode: secret
    secretKey: RETH_NODEKEY
  signer:
    type: localFile
    localFile:
      secretKey: RETH_SEQUENCER_SIGNER_PRIVATE_KEY

externalSecrets:
  secret-env:
    provider: aws
    data:
      - remoteRef:
          key: scroll/l2-sequencer-reth-0-secret-env
          property: RETH_NODEKEY
        secretKey: RETH_NODEKEY
      - remoteRef:
          key: scroll/l2-sequencer-reth-0-secret-env
          property: RETH_SEQUENCER_SIGNER_PRIVATE_KEY
        secretKey: RETH_SEQUENCER_SIGNER_PRIVATE_KEY
    refreshInterval: 2m
    serviceAccount: external-secrets
```

`secret-env` is a logical values key. The Chart renders its SecretStore,
ExternalSecret, and target Secret as `<release-fullname>-secret-env`; ConfigMap,
Service, StatefulSet, and PVC names are likewise release-derived. Do not set
`global.nameOverride` or `global.fullnameOverride` in normal production values.
For an AWS KMS sequencer, retain an explicit `serviceAccount.name` when the EKS
IRSA role trust policy pins that namespace/ServiceAccount OIDC subject.
